# 2차 스프린트 킥오프 리팩토링 합의안

작성: 2026-10-21 / 상태: 팀 합의를 위한 초안. 체크 항목은 미완료이며 이름 예시는 제안이다.

## 합의·수행·검증의 구분

|구분|킥오프에서 합의할 내용|2차 스프린트에서 수행할 내용|
|---|---|---|
|패키지/명명|업무 경계·공통 책임·타입/멤버 규칙·이름 대응표|패키지→소스/타입→멤버→구현 변경·참조 점검|
|계층/생성|Controller·Service·Mapper/Repository 책임·DI 규칙|ActionFactory/Action·Connection/SQL 책임 전환|
|예외|예외 종류·처리 위치·상태/문구·로그·롤백|공통 처리 구현·실패 시나리오 테스트·검증|
|데이터 접근/DB|MyBatis/JPA 적용 근거·DB 선택 기준·쓰기 책임|연동·이관/호환성·데이터 정합성·복구 검증|
|계정/화면|BCrypt 계약·형식/마스킹·메인 경로·HTML 정리 기준|구현·기존 계정/화면 회귀·미사용 파일 정리|
|협업|페어·PR·회의 목적·결정 근거·완료 기준|데일리 기록·교차 리뷰·테스트·발표 근거 정리|

킥오프는 규칙의 최소 기준과 담당·미결 사항을 정하는 시점이다. 기능 상세는 10/26~28 업무별 설계에서 구체화하고 변경 이유를 기록한다. Jira의 체크리스트는 수행 후 증거와 함께 완료 처리한다.

## 명명·구조 체크리스트

킥오프 명명·구조 변경 체크리스트

이름 변경의 실행 순서: 현행 동작·기준 결과와 이름 대응표 고정 → 패키지 → 소스 파일/타입 → 멤버/메서드 → 구현·설정·화면 참조 → 컴파일·테스트. 패키지명 변경만으로 DB 테이블·컬럼명이나 외부 URL을 함께 바꾸지 않는다. 변경이 필요하면 별도 매핑·영향·검증을 기록한다.

- [ ] 업무 단위 패키지와 허용 의존 방향을 합의한다. 예: <base>.compensation, .producer, .damageapplication, .disastercode, .account. 업무 패키지 안에 controller/service/mapper/repository/dto/entity를 필요한 범위로 둔다.
- [ ] shared/common에는 config·exception·format·security 등 여러 업무에서 실제 재사용하는 기술 책임만 둔다. 재해코드는 업무 책임이 드러나는 disastercode 패키지로 구분한다.
- [ ] 모든 이름의 현재→변경→업무 의미→영향 파일/설정→담당/리뷰→검증 결과 대응표를 만든다. 실제 기본 패키지와 최종 이름은 팀이 합의한다.
- [ ] 소스 파일·타입 이름은 PascalCase와 일치시키고 compensationDetailAction처럼 규칙이 어긋난 타입을 식별한다. Spring 전환 시 요청 처리 책임에 맞는 CompensationDetailController 등으로 대응한다.
- [ ] 메서드/변수는 lowerCamelCase, 상수는 UPPER_SNAKE_CASE로 맞춘다. 조회·등록·변경의 동사와 금액·기간·비율의 의미/단위를 공통 용어와 일치시킨다.
- [ ] 인터페이스 이름은 대상 업무/데이터와 역할을 표현한다. 제안 예: DisasterCodeProvider(재해코드 제공 계약), CompensationStatisticsQueryService(보상 통계 조회), CurrentUserProvider(현재 사용자 식별). CommonService·CodeInterface처럼 대상을 알 수 없는 이름은 정비한다.
- [ ] 인터페이스 도입은 외부 API 경계·대체 구현·책임 분리의 필요성을 기록한다. 모든 클래스에 형식적으로 인터페이스를 추가하지 않는다. Mapper·Repository·외부 API Client/Provider의 역할을 혼동하지 않는다.
- [ ] 패키지 이동·이름 변경 시 import·테스트·Spring 스캔/Bean 이름·Mapper namespace/id·XML 매핑·DTO 프로퍼티·JSP EL·URL/문자열 참조를 함께 확인한다.
- [ ] JPA Entity와 DB 테이블/컬럼 대응을 명시하고 이름 변경으로 스키마가 의도치 않게 바뀌지 않는지 검증한다. MyBatis 파라미터/결과 매핑과 UI·ERD 필드를 교차 확인한다.
- [ ] 패키지/타입/멤버 변경을 검증한 뒤 Controller·Service·데이터 접근 계층 구현을 바꾼다. 각 단계의 컴파일·회귀 결과를 남기고 PR에서 이름 변경과 동작 변경을 구분해 검토한다.
- [ ] 구조 규칙을 위반하는 기존 코드와 불가피한 예외는 사유·영향·후속 담당/기한으로 기록한다.
- [ ] 킥오프에서 업무 패키지·이름 규칙·인터페이스 계약·PR 검토 기준·역할/페어와 미결 사항을 합의하고 SCRUM-49의 전환 체크리스트로 인계한다.

## Spring 전환 항목

Spring 전환 완료 체크리스트
- [ ] ActionFactory·Action의 경로/생성/예외 책임을 Controller·DI·공통 예외 처리로 이관하고 기존 URL·세션·뷰 흐름을 확인한다.
- [ ] compensationDetailAction의 여러 DAO 조합·업무 로직을 Service로 분리하고 Controller는 요청·검증·응답을 담당한다.
- [ ] DAO의 Connection 수동 전달·자원 관리 책임을 Spring 관리 구조로 변경한다.
- [ ] DBCP 접속 설정을 외부 설정으로 관리하고 코드·로그·문서에 자격 증명을 노출하지 않는다.
- [ ] 로그인·변경·재설정·가입의 BCrypt 적용 계약과 기존 계정 전환 절차를 검증한다. 사용자의 기존 로그인 흐름이 중단되지 않도록 전환 시나리오를 남긴다.
- [ ] Statement/SQL을 합의한 MyBatis·JPA 책임으로 정리하고 파라미터 바인딩·예외·롤백을 테스트한다.
- [ ] 숫자·금액·날짜·기존 마스킹 표시 규칙을 목록/상세에 동일하게 적용하고 최종 산정금 등 UI 누락을 대조한다.
- [ ] 조회 횟수·응답 시간 측정 후 비동기 방식 필요성과 로딩/실패/중복 요청 처리를 반영한다.
- [ ] 루트/메인 Controller·뷰와 링크를 전환한 뒤 미사용 HTML을 정리하고 메뉴·직접 진입·새로고침을 확인한다.
- [ ] Lombok/Builder 적용은 생성 규칙·필수값·Entity 관계/변경 책임을 검토한 범위로 제한한다.
- [ ] 목록 보강 완료 PR은 회귀 기준으로 재사용하고 상세 조회의 남은 조건·상황별 테스트를 보강한다.

기존 목록 테스트 보강 PR #60은 완료 근거로 유지하고 회귀에 재사용한다. 상세의 미완료 테스트를 구분한다. 제외 표시된 PrivacyMaskingUtil 범위 재검토를 새 미완료 작업으로 되살리지 않고 기존 적용·표시의 회귀만 확인한다.

index.html은 main.html로 이동하고 공통 header.jsp가 main.html을 참조한다. 루트/메인 Controller·뷰·링크를 바꾼 뒤 미사용 파일을 정리한다. 이 문서 작성 과정에서 소스/HTML은 삭제하거나 변경하지 않았다.

## 예외 규칙

예외 처리 합의안 (킥오프에서 확정할 초안)

예외 분류와 사용자 응답
- 입력/검증 오류: 필드별 안내와 재입력. API/Ajax는 400을 기본안으로 사용한다.
- 대상 없음: 상세 자원 미존재는 404, 정상 조회의 빈 목록은 빈 결과로 구분한다.
- 미인증/권한 없음: 화면은 합의한 로그인 이동/접근 안내, API/Ajax는 401/403으로 구분한다.
- 중복·상태 충돌: 409 등 합의한 응답과 재시도/수정 안내를 제공한다.
- 공공 API 실패·지연: 재해코드 조회 실패와 빈 결과를 구분하고 안내/재시도/허용된 대체 경로를 정의한다. API/Ajax 응답은 502/504 등 원인에 맞는 상태를 합의한다.
- DB·예상치 못한 서버 오류: 사용자에게 내부 SQL·스택·접속 정보가 드러나지 않는 공통 안내를 제공한다. API/Ajax는 500을 기본안으로 둔다.

계층 책임과 이름
- Controller: 요청 검증·응답/화면 선택. 공통 처리는 @ControllerAdvice/@ExceptionHandler 등으로 일관되게 연결한다.
- Service: 업무 규칙·트랜잭션 경계·업무 의미가 드러나는 예외 책임. 예시 이름: DisasterCodeUnavailableException, DamageApplicationNotFoundException. 실제 타입은 필요한 범위만 합의한다.
- Mapper/Repository: DB 기술 예외를 삼켜 빈 결과/정상 응답으로 바꾸지 않는다. 외부 API Client/Provider도 실패 맥락을 보존한다.
- HTML 화면과 Ajax/API 각각의 응답 형식·필드·오류 코드·사용자 문구를 정의하고 정상 빈 결과와 장애를 구분한다.

로그·롤백
- 오류 맥락·원인·요청 식별 정보를 필요한 수준으로 남기고 중복 로깅·printStackTrace 의존을 정비한다.
- 비밀번호·DB 자격 증명·토큰·개인정보 원문은 로그와 사용자 응답에 남기지 않는다. 기존 마스킹 규칙을 재사용한다.
- Service 트랜잭션 범위·예외 재전파·rollbackFor 등 롤백 기준을 합의하고 부분 저장/중복 저장/성공 오인 응답을 방지한다.

구현·검증 연결
- SCRUM-47: 예외 표·패키지/타입명·응답 형식·로그/롤백·허용 예외를 합의한다.
- SCRUM-49·71 및 기능 구현: 규칙을 구현하고 각 실패 경로의 단위/연동 테스트를 남긴다.
- SCRUM-63·64·65: 전체 흐름의 실패·권한·API 지연·DB 롤백·사용자 안내를 테스트·교차 검증·재검증한다.
- 완료 증적: 입력/상황 → 기대 상태·문구·DB 상태 → 실제 결과 → 수정/수용 근거. 규칙 변경은 결정 이유·영향 Jira·담당/기한을 기록한다.

Spring의 공통 처리 수단 참고: [예외 처리 문서](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-controller/ann-exceptionhandler.html). 적용 버전은 팀이 정한 Spring 버전에 맞춰 확인한다.
