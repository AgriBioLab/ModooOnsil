# 화훼 생산자 서비스 — 핵심기능·필수/선택·UML 개념 모델

이 문서는 구현 완료 보고서가 아닌 2차 스프린트의 요구사항 및 모델 설계안이다.

## 1. 개요와 니즈

개요: 보상 금액 산정에 필요한 화훼 농민 정보를 확보하기 위해, 농민이 농장 정보와 재배·출하 이력을 간편하게 관리하고 축적된 기록으로 피해보상을 신청할 수 있는 서비스를 제공한다.

생산자 니즈: 피해보상 신청 시 기존 기록을 활용하고 싶다. 이를 위해 농장 정보와 재배·출하 이력을 간편하게 관리하고 싶다.

이번 설계 범위는 생산자 정보·영농기록 관리와 기존 기록을 활용한 피해보상 신청이다. 피해 판정, 금액 산정, 지급, 품질담당자의 추가 분석기능은 이번 필수·선택 범위에 넣지 않는다. 1차는 품질담당자의 로그인 및 피해보상 지급결과 목록·검색·상세 조회 기능이다. 앞선 버전의 '피해보상 신청은 후속'이라는 구분은 니즈와 맞지 않아 수정했다.

## 2. 핵심과 우선순위

핵심은 서비스 목적에 직접 기여하는 업무이고, 필수/선택은 이번 스프린트의 구현 우선순위다. UML 자체에는 이 세 가지를 구분하는 표준 선 종류가 없다. 아래 ID와 색상은 프로젝트의 표시 규칙이다.

| ID | 핵심 여부 | 우선순위 | 유스케이스 | 요구사항 |
|---|---|---|---|---|
| UC-01 | 핵심 업무 | 필수 | 생산자·농장 정보를 관리한다 | 본인 기본정보와 농장·온실의 위치·면적을 등록·조회·수정한다. |
| UC-02 | 핵심 업무 | 필수 | 화훼 재배현황을 관리한다 | 재배구역·품종·면적·정식일·재배단계를 관리한다. |
| UC-03 | 핵심 업무 | 필수 | 재배공정·작업기록을 관리한다 | 재배 건에 작업일자·수행내용·생육상태를 기록하고 조회·수정한다. |
| UC-04 | 핵심 업무 | 필수 | 출하이력을 관리한다 | 재배 건에 출하일·품종·수량·단위를 기록하고 조회·수정한다. |
| UC-05 | 핵심 업무 | 필수 | 재배·출하 이력을 조회한다 | 기간·품종·재배구역으로 본인의 기록을 검색하고 상세내용을 확인한다. |
| UC-06 | 공통 기반 | 필수 | 로그인한다 | 본인 계정으로 인증한다. |
| UC-07 | 공통 기반 | 필수 | 로그아웃한다 | 세션을 종료한다. |
| UC-08 | 편의 기능 | 선택 후보 | 기록에 사진을 첨부한다 | 생육상태와 작업상황을 사진으로 남긴다. |
| UC-09 | 편의 기능 | 선택 후보 | 조회한 기록을 내려받는다 | 조회한 기록을 파일로 저장한다. |
| UC-10 | 편의 기능 | 선택 후보 | 재배·출하 기록을 비교한다 | 재배기간별 작업내역 및 출하수량을 비교한다. |
| UC-11 | 핵심 업무 | 필수 | 기존 기록으로 피해보상을 신청한다 | 본인·농장 정보를 불러오고 기존 이력을 조회·선택한 뒤 피해내용을 추가하여 신청서를 제출하고 접수번호를 확인한다. |

선택기능 중 일정 알림은 별도 후보로 보류한다. 본 설계안에서는 외부 서비스 연동 없이 가능한 사진·내려받기·기록 비교를 대표 후보로 표시한다. 선택 후보 전부를 구현한다는 의미는 아니다.

## 3. 액터와 시스템 경계

| 대상 | 모델에서의 처리 | 이유 |
|---|---|---|
| 화훼 농민 | 2차의 주 액터 | 시스템 밖에서 자신의 정보를 관리하는 사용자 역할이다. |
| 품질담당자 | 전체 개념도에 표시하는 1차 액터 | 지급결과 목록·검색·상세조회에 참여한다. 2차 기록관리 기능의 액터로 임의 추가하지 않는다. |
| 공공기관 | 서비스 제공 주체 | 운영기관 자체를 추가 액터로 그리지 않는다. 기관 담당자의 실제 사용자 역할이 있으면 그 역할을 액터로 정의한다. |
| 우리 시스템·내부 DB·웹 서버·내부 배치 | 시스템 액터로 추가하지 않음 | 현재 모델의 내부 구성요소이며 시스템 경계 밖의 상호작용 주체가 아니다. |
| 외부 본인인증 서비스 | 연동 확정 시 보조 시스템 액터 | 자체 계정 인증만으로 구현하면 불필요하다. |
| 외부 농업경영체 정보 시스템 | 데이터 연동 확정 시 보조 시스템 액터 | 실제 API·권한·연계 범위를 확인한 후 '등록정보를 불러온다' 등의 유스케이스에 연결한다. |
| 외부 보상처리 시스템 | 별도 시스템과 연동 확정 시 보조 시스템 액터 | 동일 시스템 안의 1차 모듈은 외부 액터가 아니다. 피해보상 업무가 있다는 이유만으로 연동을 가정하지 않는다. |

현재 확정된 기능을 모델링할 때 시스템 액터는 필요하지 않다.

## 4. UML 표기 적용

- 액터는 시스템 경계 밖에, 유스케이스는 경계 안에 놓는다.
- 유스케이스 이름은 화면명이나 데이터명보다 '재배현황을 관리한다'처럼 사용자 목적을 드러내는 동사형으로 쓴다.
- 액터와 유스케이스는 실선 연관으로 연결한다. 이 선은 데이터 흐름이나 실행 순서가 아니다.
- 핵심·필수·선택은 표와 색상 범례로 표시한다. 파랑=핵심·필수, 회색=공통·필수, 노랑=선택 후보다. 이는 UML 표준 색상 규칙이 아닌 프로젝트 규칙이다.
- `include`는 기본 유스케이스의 행동에 다른 유스케이스의 행동을 포함할 때 사용하며 화살표는 기본 → 포함되는 유스케이스다. 단순 선행조건이나 필수기능 표시가 아니다.
- `extend`는 독립적으로 성립하는 기본 유스케이스의 특정 확장점에 추가 행동을 삽입할 때 사용하며 화살표는 확장 → 기본 유스케이스다. 선택 개발 항목이라는 이유만으로 사용하지 않는다.
- 로그인은 UC-06으로 따로 표시하고 업무 유스케이스에 '로그인 완료 및 본인 기록 접근권한 보유'라는 사전조건을 둔다. 모든 업무에서 다시 로그인하는 흐름이 아니므로 일괄 `include`하지 않는다.
- UC-11의 신청 과정에서 기존 재배·출하 이력을 조회·확인하는 UC-05를 항상 수행하는 흐름으로 정의했다. 따라서 `UC-11 ..> UC-05 : <<include>>`를 표시했다. 기존 기록의 신청서 반영 여부 선택은 UC-11의 후속 단계다. UC-01 '정보 관리'나 UC-03 '작업기록 관리'는 신청 중 매번 수행하지 않으므로 include하지 않는다.
- `extend`는 현재 개념도에 사용하지 않는다. 선택기능의 확장점과 실행 흐름을 구체화한 뒤 필요할 때만 추가한다.
- 등록·수정·조회의 세부 행동은 관리 유스케이스 명세에 기술한다. 현재 단계에서 모든 버튼과 CRUD 동작을 별도 타원으로 분해하지 않는다.

### 상세화할 때의 extend 예시

UC-05의 기본 흐름이 '조건 입력 → 결과 목록 확인 → 상세내용 확인'으로 끝나고, 확장점을 '조회 결과를 확인한 시점'으로 정의했다고 가정한다. 그 지점에서 사용자가 파일 저장을 요청할 때 UC-09를 실행한다면 `UC-09 ..> UC-05 : <<extend>>`로 모델링할 수 있다. 조건은 '사용자가 내려받기를 요청함'이며, 파일을 받지 않아도 조회 목적은 달성된다. 이 실행 흐름을 확정하기 전에는 현재 개념도의 직접 연관만 유지한다.

## 5. 핵심 유스케이스 명세 예시

### UC-11 기존 기록으로 피해보상을 신청한다

- 주 액터: 화훼 농민
- 목표: 평소 관리한 생산자·농장·재배·출하 기록을 재사용해 피해보상 신청서를 제출한다.
- 사전조건: 로그인 완료, 본인이 관리할 수 있는 생산자·농장·재배정보 존재.
- 기본 흐름: ① 피해보상 신청 시작 ② 본인·농장 기본정보 불러오기 ③ UC-05로 기존 재배·출하 이력 조회·확인 ④ 관련 기록 선택 ⑤ 피해 발생일·위치·품종·피해내용 등 사건별 정보 추가 ⑥ 반영된 기록과 신청내용 최종 확인 ⑦ 제출 ⑧ 접수번호 확인.
- 대안 흐름: 기존 이력 조회 결과가 없으면 해당 사실을 안내하고 기록 보완 또는 수동 기재 후 다시 제출하도록 한다. 조회 자체는 항상 수행된다. 필수값 누락 시 보완을 요청한다. 제출 실패 시 접수 완료로 표시하지 않으며, 재시도 시 중복 신청을 방지한다.
- 사후조건: 신청번호가 생성되고 신청자·피해대상·피해내용 및 선택한 기록이 연결된다. 신청 시점의 기본정보와 선택 기록의 내용 또는 버전을 보존한다.
- 범위 경계: 신청 접수는 보상 승인·금액 산정·지급 완료를 의미하지 않는다. 산정·심사·지급은 별도 업무이며 품질담당자에게 이번에 임의로 부여하지 않는다.
- 증빙 요구: 필수 증빙 종류 및 사진 필수 여부는 별도 업무규칙에서 확정한다. 일상 기록의 선택적 사진 첨부 기능과 신청의 필수 증빙을 구분한다.

### UC-03 재배공정·작업기록을 관리한다

- 주 액터: 화훼 농민
- 목표: 특정 화훼 재배 건의 작업 및 생육기록을 남겨 재사용한다.
- 사전조건: 로그인 완료, 본인이 관리할 수 있는 농장·재배 건 존재.
- 기본 흐름: ① 농장과 재배 건 선택 ② 작업일자·종류·내용·생육상태 입력 ③ 시스템이 필수값 및 접근권한 확인 ④ 기록 저장 ⑤ 저장된 기록 확인.
- 대안 흐름: 필수값 누락 시 보완 안내. 재배 건이 없으면 UC-02에서 먼저 등록. 저장 실패 시 실패 사실을 알리고 재시도할 수 있게 함.
- 사후조건: 작업기록이 생산자·농장·재배 건에 연결되어 조회 가능하다.
- 기록 신뢰성 요구: 작성시각과 실제 작업일자를 구분한다. 수정 시 이전 값을 추적할 수 있도록 한다. 입력된 기록 자체를 피해보상 자격이나 금액의 확정 증거로 취급하지 않는다.

## 6. 1차와 연결되는 정보 개념

생산자 → 농장·재배구역 → 화훼 재배 건 → 작업기록·출하이력으로 기록을 연결한다. 2차 피해보상 신청 건은 신청자·피해대상 재배 건과 선택한 기존 기록을 참조한다. 현재 정보 수정이 이미 제출한 신청의 기준정보를 덮어쓰지 않도록 제출 시점의 정보 또는 버전을 보존한다.

전체 서비스 개념도에서는 화훼 농민의 기록관리·보상 신청과 품질담당자의 보상결과 조회를 같은 시스템 경계 안에 둔다. 보상 신청 → 심사·산정 → 지급 → 결과조회라는 전체 업무에는 이번에 구현하지 않는 중간 단계가 있다. 2차 신청만으로 1차의 지급완료 결과가 자동 생성되는 것으로 모델링하지 않는다. UC-11과 UC-05 사이의 include는 신청 도중 이력 조회를 수행한다는 의미이며, 신청과 결과조회 사이의 데이터 공유나 진행 순서를 표현하는 것이 아니다.
