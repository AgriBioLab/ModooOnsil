### 사용자 설명으로 구체화한 2차 기능 범위

아래는 사용자 설명을 반영한 기능 계획이다. 재해코드의 공공기관 API 연계, 기존 보상 지급결과 상세의 서류파일 열람, 전년도 대비 비교분석의 업무 목적을 반영했다. 세부 명세·담당자·일정까지 확정된 상태는 아니다. ‘가이부터’는 문맥상 ‘가입부터’로 해석했다.

| 액터 | 업무 구분 | 2차 추가 구상 | 명세에서 정할 내용 |
|---|---|---|---|
| 품질담당자(주 액터) | 통계 조회 | 예산 수립 등 업무 의사결정을 위한 보상·피해 관련 통계 조회 | 집계 대상, 기간·지역·품목·재해유형 등의 필터, 건수·금액 등 지표 |
| 품질담당자(주 액터) | 비교분석 조회 | 전년도 대비 현황·변화를 비교하여 예산 수립 등 의사결정 지원 | 전년 전체 또는 동일 기간 비교 여부, 비교 지표와 집계 기준 |
| 품질담당자(주 액터) | 서류 열람 | 기존 보상 지급결과 조회 상세에 연결된 서류파일 열람 | 실제 파일 연결, 미리보기·다운로드 방식, 열람 권한 |
| 품질담당자(주 액터) | 계정 관리 | 마이페이지, 비밀번호 찾기·변경 | 마이페이지 표시 정보, 로그인 전 재설정 경로, 로그인 후 변경 절차 |
| 생산자(추가 부 액터) | 가입 | 생산자 회원가입 | 필수 정보, 가입 완료 조건, 로그인 방식 |
| 생산자(추가 부 액터) | 피해신청 | 공공기관 API에서 불러온 재해코드를 피해신청에 연결 | API명·응답 필드, 코드 선택 방식, 필수 입력, 첨부 여부, 제출 완료 조건 |
| 생산자(추가 부 액터) | 본인 신청 조회 | 본인이 제출한 피해신청 조회 | 목록·상세 범위, 표시 정보, 본인 식별 기준 |

비밀번호 찾기는 로그인 전 ‘비밀번호 재설정’ 흐름으로, 변경은 로그인 후 마이페이지 흐름으로 구분하는 안을 제안한다. 기존 비밀번호를 보여주는 기능으로 정의하지 않는다. 생산자 계정에도 같은 기능을 제공할지는 별도 결정한다.

생산자의 피해신청 수정·취소, 품질담당자의 접수·승인·보상금 지급 기능은 이번 설명에 포함되지 않았다. 필요 여부를 논의하기 전까지 추가 범위에 넣지 않는다.

### 액터별 워크플로우 초안

품질담당자:

1. 로그인 후 기존 보상 지급결과 조회 또는 신규 통계·비교분석 화면으로 진입한다.
2. 통계에서는 조건을 선택해 집계 결과를 조회한다. 비교분석에서는 전년도 대비 현황·변화를 확인하여 이후 예산 수립 등 업무 의사결정의 근거로 활용한다.
3. 보상 지급결과 목록에서 상세로 진입해 해당 건에 연결된 기존 서류파일을 열람한다.
4. 마이페이지에서 계정 정보를 확인하고 비밀번호를 변경한다. 비밀번호를 잊은 경우 로그인 화면의 재설정 경로를 이용한다.

생산자:

1. 회원가입 후 로그인한다. 로그인은 본인 신청을 구분하기 위한 선행 기능으로 제안한다.
2. 피해신청 화면에서 공공기관 API로 불러온 재해코드를 선택·연결하고 피해 정보를 입력한다. 코드 선택 UI와 API 호출·갱신 시점은 후속 설계에서 정한다.
3. 신청을 제출하고 완료 결과를 확인한다.
4. 본인 신청내역을 조회한다. 목록·상세 구성은 후속 명세에서 결정한다.
5. 다른 생산자의 신청 식별자로 요청하더라도 해당 내역을 조회할 수 없는지 확인한다.

### 재해코드 공공 API 연계

재해코드는 공공기관 API에서 불러오는 것으로 사용자가 정했다. 생산자가 새로운 공통 코드를 직접 생성하는 기능은 계획에 포함하지 않는다. 워크플로우의 외부 연계 지점은 생산자의 피해신청 단계다.

외부 연계 흐름 초안: 피해신청 화면 진입, 서비스의 재해코드 데이터 준비, 공공기관 API 응답의 코드·명칭 제공, 생산자의 코드 선택, 피해신청과 코드 연결, 본인 신청내역 조회. API를 요청마다 직접 호출할지, 서버에 저장·갱신할지는 미정이다. 제공기관/API명과 응답 구조를 확인한 뒤 정한다.

비교분석 화면의 외부 API 연계는 별도로 요청되지 않았다. 전년도 대비 분석은 내부 집계 데이터의 범위와 기준을 먼저 정한다.

### 통계·비교분석의 업무 목적과 명세 제안

품질담당자는 피해·보상 현황과 전년도 대비 변화를 조회하고, 이를 이후 예산 수립 및 업무 의사결정의 근거로 활용한다. 자동 예산 산정이나 미래 예측은 현재 기능 범위로 정하지 않았다.

명세 제안:

- 통계 조회는 선택한 기간의 현황을, 비교분석 조회는 전년도 대비 변화를 설명하도록 구분한다.
- 비교 지표 후보는 피해신청 건수, 보상 지급 건수, 보상 지급금액이다. 실제 채택 지표는 팀이 결정한다.
- 당해 연도 중간 집계라면 전년도 동일 기간과 비교하는 방식을 우선 검토한다. 신청일과 지급일 중 어느 날짜로 집계하는지, 지급 완료 등 어떤 상태를 포함하는지도 함께 명시한다.
- 증감 건수·금액과 증감률의 표시 여부를 정한다. 증감률을 표시한다면 전년도 값이 0일 때의 표시 방식을 정의한다.
- 새 피해신청 데이터와 지급 완료 데이터를 구분한다. 신청 제출만으로 보상 지급 실적에 포함하지 않는다.

### 강사님 보고용 기능 범위 설명 초안

“2차 스프린트에서는 품질담당자가 예산 수립 등 업무 의사결정에 활용할 수 있도록 통계 조회와 전년도 대비 비교분석 조회를 추가할 계획입니다. 기존 보상 지급결과 상세에 연결된 서류파일 열람과 마이페이지·비밀번호 관리 기능도 보완합니다. 추가 부 액터는 생산자로 설정하고, 회원가입부터 공공기관 API에서 불러온 재해코드를 활용한 피해신청, 본인 신청내역 조회까지 구현할 계획입니다. 이 기능 범위에 Spring 전환과 1차 보완 과제를 함께 반영해 일정과 역할을 정리하겠습니다.”

### 페르소나와 액터 정리 기준

페르소나는 대표 사용자의 상황과 필요를 구체화한다. 액터는 시스템과 상호작용하는 역할이며 권한·업무 흐름을 정할 때 사용한다. 외부 API 제공 시스템은 사람 페르소나와 구분해 표시한다.

신규 액터를 추가하면 누가 어떤 업무를 수행하는지, 어떤 데이터까지 조회·등록·수정할 수 있는지 함께 결정한다. 액터 이름만 추가하고 업무·권한을 비워두지 않는다.

### 공공 API를 포함하는 워크플로우 페이지

API를 사용하는 각 화면에 다음 내용을 붙인다.

| 항목 | 작성할 내용 |
|---|---|
| 사용자·시작 조건 | 누가 어떤 목적으로 화면에 진입하는가 |
| 입력 | 사용자가 선택·입력하는 조건 |
| 기존 데이터 처리 | 내부 DB에서 조회하거나 변경하는 정보 |
| 외부 연계 지점 | 어느 단계에서 어떤 공공 API를 호출하는가 |
| 결과 활용 | 어떤 필드를 화면에 표시하고 저장하는가 |
| 예외 흐름 | 결과 없음, 응답 지연·실패, 호출 한도 초과 시 화면 동작 |
| 완료 조건 | 정상·빈 결과·실패 시나리오에서 확인할 결과 |

공공기관 API의 재해코드를 피해신청에 활용한다는 연계 목적은 정해졌다. 구체 API명·공식 문서는 아직 제공받지 않았다. 제공 데이터, 키 발급·이용 조건, 호출 한도·갱신 주기는 선정할 API의 공식 문서로 별도 확인한다. API 데이터가 실제로 뒷받침하지 않는 보상 판정이나 자동화를 약속하지 않는다.

## 3. 1차 후속 과제 후보

아래는 10월 18일 리뷰에 기록된 항목이다. 킥오프 전 현재 통합본에서 수정 여부를 재확인하고, 미해결 항목만 백로그에 반영한다.

| 후보 | 보고할 영향과 완료 기준 제안 |
|---|---|
| 로그인·목록의 static DAO/Connection과 연결 해제 | 요청 간 상태 공유와 연결 관리 보완. 요청별 DB 자원 책임을 정하고 정상·예외 경로의 해제를 확인 |
| DAO 오류와 정상 빈 결과의 혼동 | 인증 실패·조회 결과 없음·DB 오류를 구분하고 사용자 응답과 로그를 확인 |
| 직접 JSP 접근 보호 | 비로그인 상태에서 보호 화면에 직접 접근하는 시나리오 확인 |
| 조사 이력 조회 기준 | 복수 이력에서 어떤 행을 표시할지 업무 기준을 정하고 화면 간 일관성 확인 |
| 기존 상세의 서류파일 열람 | 사용자가 2차 보완 범위로 제시. 파일 연결·열람 방식·접근 권한을 확인하며 다운로드 제공 여부는 별도 결정 |
| 테스트 보완 | 기존 핵심 흐름의 회귀 확인에 검색 조건·빈 결과·입력 오류·외부 API 실패 시나리오 추가 |

문서와 코드의 불일치도 정리 대상이다. 예를 들어 기존 협업 문서는 상세 파라미터를 `no`로 안내하지만 제출본 리뷰의 실제 상세 흐름은 `appId`를 사용한다. 규칙의 이름만 고치지 말고 업무 식별자, URL, 호출부와 문서를 함께 맞출 기준을 합의한다.

## 4. Spring 전환·규칙 보완 제안

현재 제출본 리뷰의 요청 흐름은 FrontController, ActionFactory, Action, DAO, VO, JSP로 이어지며 별도 Service 계층은 없다. README의 전환 예정 설명과 실제 구현 상태를 구분해서 보고한다.

전환 논의 순서:

1. 강의·제출 환경에 맞는 Spring 구성과 버전을 정한다.
2. 기존 핵심 화면과 요청·세션·DB 동작을 전환 기준으로 기록한다.
3. 대표 조회 기능 하나로 프로젝트 실행, 요청 처리, DB 연결, 화면 표시를 확인한다.
4. 나머지 기능의 전환 담당과 병합 순서를 정한다.
5. 기존 로그인·검색·상세·로그아웃 흐름과 오류 응답을 다시 확인한다.

규칙 초안은 채택할 구조와 함께 결정한다. 단순한 예시로 클래스는 `CompensationDetailController`, 메서드·변수는 `getCompensationDetail`·`appId`처럼 의미와 표기를 일치시킬 수 있다. 이는 이번 문서의 제안이며 확정된 파일명이나 패키지 구조가 아니다. DB 접근 방식에 따라 DAO/Repository 등의 명칭을 결정한다.

합의 문서에는 패키지 책임, 파일·클래스명, 약어 표기, 업무 용어, URL·파라미터, 예외 처리, 설정 관리, 테스트 위치, Git·PR 규칙을 포함한다. 기존 규칙은 변경 이유와 적용 예시를 남겨 보완한다.

## 5. 일정 구성안

실제 날짜와 소요 기간은 미정이다. 기능 추가와 전환 작업을 함께 고려해 아래 순서의 마일스톤을 제안한다.

| 단계 | 주요 작업 | 다음 단계 진입 기준 |

| 착수 | 팀장 인수인계, 온보딩, 필수 범위·기술 결정 | 담당자와 개발환경 준비 |

## 8. 협업·권한·보고 운영 권장안

사용자 요청에 따라 다음 운영안을 Google Slides 12~15장과 17장에 반영했다. 실제 GitHub 저장소·Issues·Projects·권한 설정을 생성하거나 변경한 작업은 아니다.

- 상세 기록은 공용 저장소의 Markdown 문서로 관리한다. 회의록에는 논의·결정·이유·담당·기한을, 피드백에는 지적사항·조치·검증·미결사항을 기록한다.
- 업무 상태와 완료 조건은 Issues·Projects를 기준으로 관리한다. 문서와 별개인 상태 목록을 중복 갱신하지 않는다. 날짜 필드·로드맵으로 일정을 표시하고 PR과 검증 근거를 연결한다.
- 상태 흐름은 할 일 / 진행 중 / 검토 / 완료를 제안한다. 갱신 주기와 완료 처리 권한은 킥오프에서 합의한다.
- 공용 문서와 열람 대상이 다른 문서는 저장소를 분리한다. 조직 저장소의 팀원 Write / 강사 Read는 역할 예시이며 실제 조직·팀 기본 권한까지 확인해야 한다. 폴더·브랜치·CODEOWNERS로 문서별 열람 제한을 구현할 수 없다.
- 문서마다 다른 공유 권한이 필요하면 Confluence·Notion을 대안으로 검토한다. 요금제와 권한 기능을 확인한 뒤 기준 도구를 정한다.
- 발표·중간 보고는 기존 Google Slides 템플릿에 핵심 내용을 요약하고 16:9(720×405pt) PDF로 제출한다. 보고일·버전·원본·Issue 링크를 보고 목록에 남긴다.
- PDF에서는 한글·Regular/Bold·제목 위계·표·도식·줄바꿈·잘림을 확인한다. 반복 보고가 늘면 Markdown과 공통 CSS 테마를 사용하는 GitHub + Marp 자동화를 후속 검토한다.
