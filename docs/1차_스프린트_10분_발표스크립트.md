사용법: 대괄호 안의 내용은 진행 지시이므로 읽지 않습니다. 시간은 리허설용 목표입니다.

## 1장 · 표지 [0:00~0:20]

안녕하세요. 2조의 농산물 피해 보상 모니터링 서비스, 1차 스프린트 결과를 발표하겠습니다.

저희 팀은 이재숙, 이원규, 김민경, 박건태 네 명으로 구성되어 있습니다. 이번 발표에서는 서비스의 목적과 구현 범위, 설계와 개발 결과, 그리고 다음 스프린트에서 개선할 점을 말씀드리겠습니다.

## 2~3장 · 목차 [0:20~0:35]

발표는 프로젝트 소개, 아키텍처와 협업 규칙, 데이터 모델링, 구현 결과, 회고 순서로 진행하겠습니다.

먼저 어떤 사용자의 업무를 지원하려고 했는지부터 설명드리겠습니다.

[프로젝트 소개 구분 페이지는 짧게 넘깁니다.]

## 4장 · 서비스 개요 [0:35~1:15]

저희 서비스는 농산물 피해에 대한 보상 처리 결과와 유형별 통계를 조회하는 웹 서비스입니다.

품질 담당자가 보상금 지급 결과를 확인하고, 기간이나 지역, 품목, 재해 유형별로 예산 집행 현황을 파악하는 것이 전체 서비스의 목적입니다. 이렇게 확인한 정보는 향후 예산을 계획하고 확보하는 근거로 활용할 수 있습니다.

이번 1차 스프린트에서는 품질 담당자의 로그인과 보상 처리 지급결과 목록, 상세 조회를 구현 범위로 정했습니다. 통계와 분석은 전체 서비스에 포함되는 기능이며, 이번 발표에서는 조회 업무를 중심으로 설명드리겠습니다.

## 5~7장 · 페르소나, 워크플로우, UI 프로토타입 [1:15~2:05]

주 사용자는 품질 담당자입니다. 생산자와 판매자, 유통자는 보상 업무에 관련된 부 액터이며, 자료에서는 생산자를 대표로 설정했습니다.

품질 담당자에게 필요한 것은 여러 보상 건 중 확인할 대상을 찾고, 해당 건의 지급 결과와 관련 정보를 파악하는 것입니다.

이를 기준으로 사용자 흐름을 로그인, 보상 처리 결과 목록 조회, 상세 조회로 정리했습니다.

UI 프로토타입도 이 흐름에 맞춰 세 화면으로 구성했습니다. 목록에서는 조건을 입력해 대상을 찾고, 상세에서는 선택한 건의 신청과 산정, 지급 관련 정보를 확인하도록 했습니다.

이 세 화면을 기준으로 필요한 업무와 데이터를 구체화했습니다.

[5장에서는 사용자, 6장에서는 흐름, 7장에서는 세 화면을 가리킵니다.]

## 8~9장 · 일정관리와 아키텍처 전환 [2:05~2:30]

일정은 분석, 설계, 구현 단계로 나누어 진행했습니다. 분석에서는 사용자의 업무와 범위를 정리하고, 설계에서는 UI 명세와 데이터 구조를 구체화했습니다.

구현 단계에서는 설계 내용을 실제 화면과 조회 기능으로 연결했습니다. 진행 중에는 데일리 회의를 통해 작업 상황과 필요한 논의를 공유했습니다.

이어서 시스템 구조를 설명드리겠습니다.

[아키텍처 구분 페이지를 넘깁니다.]

## 10장 · 시스템 구성 및 요청 흐름 [2:30~3:20]

시스템은 톰캣에서 동작하며, 요청 처리와 데이터 조회, 화면 표시의 역할을 나누었습니다.

품질 담당자가 브라우저에서 요청하면 프론트 컨트롤러가 요청을 받습니다. 액션 팩토리는 요청에 맞는 액션을 선택하고, 해당 액션이 필요한 처리를 수행합니다.

데이터 조회는 DAO가 담당하며, DBCP를 통해 데이터베이스 연결을 사용하고 오라클에서 필요한 정보를 가져옵니다. 조회 결과는 JSP 화면으로 전달하고, EL과 JSTL을 이용해 표시합니다.

예를 들어 목록에서 상세 화면으로 이동하면, 선택한 건의 식별정보를 받아 관련 데이터를 조회하고 상세 화면에 보여주는 방식입니다.

이 구조를 통해 화면 표시와 조회 로직의 담당 위치를 구분했습니다.

## 11~15장 · 협업·개발 규칙 [3:20~4:15]

협업에서는 브랜치와 PR, 커밋 규칙을 먼저 정했습니다.

기능별 브랜치에서 개발한 뒤 dev 브랜치로 PR을 올리고, 리뷰어 한 명의 승인을 받아 병합하도록 했습니다. main 브랜치는 제출용으로 구분했습니다.

PR에는 구현한 UI와 업무, 확인 방법을 작성하고 체크리스트로 점검하도록 했습니다. 커밋도 기능 추가나 오류 수정처럼 목적에 따라 구분하고, 하나의 커밋에는 하나의 목적을 담도록 했습니다.

또 하나 중요했던 것은 공통 용어입니다. 같은 업무를 서로 다른 표현으로 이해하는 문제가 있어, UI 명세와 모델링에서 사용하는 한글 업무명과 영문명을 맞췄습니다.

변수와 메서드, 상수의 표기 기준도 정했습니다. 이를 통해 문서에서 설명하는 업무를 코드에서도 같은 의미로 찾을 수 있도록 했습니다.

[Git 저장소와 PR 템플릿은 핵심 위치만 짚고 넘깁니다.]

## 16~17장 · ERD [4:15~5:00]

다음은 데이터 모델링입니다.

ERD는 농산물 피해신청을 중심으로 신청자, 현장조사, 피해조치, 보상신청 정보를 연결했습니다. 보상신청에는 보상금 산정과 지급 정보를 연결하고, 각 단계에서 사용하는 서류도 구분했습니다.

이 관계가 필요한 이유는 상세 화면에서 지급 결과와 함께 그 결과에 연결된 신청, 조사, 조치 정보를 확인해야 하기 때문입니다.

예를 들어 하나의 피해신청번호로 해당 신청의 보상 정보를 찾고, 연결된 산정 결과와 지급 내역을 조회할 수 있도록 구성했습니다.

화면에서 필요한 정보가 데이터 구조에 있는지 확인하면서 UI 명세와 ERD를 함께 검토했습니다.

## 18~20장 · 업무명세서와 클래스 다이어그램 [5:00~5:50]

이번 스프린트의 업무명세는 UI 세 개, 업무 스물한 개, SQL 스물한 개로 정리했습니다.

각 업무에는 입력과 출력을 정의했습니다. 로그인에는 아이디와 비밀번호가 필요하고, 목록 조회에는 지급일이나 피해신청번호 등 검색 조건이 필요합니다. 상세 조회에서는 선택한 건의 신청과 산정, 지급 정보를 가져옵니다.

이 명세를 바탕으로 클래스의 역할을 나누었습니다. 공통 요청은 프론트 컨트롤러와 액션 팩토리가 처리하고, 기능별 액션은 로그인과 목록, 상세 요청을 담당합니다.

DAO는 데이터 조회를 맡고, VO는 조회한 정보를 전달합니다. 업무명세에 정의한 입출력이 코드의 어느 부분으로 이어지는지 확인하며 구현했습니다.

## 21장 · 단위테스트 [5:50~6:30]

단위테스트는 총 스물다섯 개입니다. 상세 DAO 스물한 개, 목록 DAO 두 개, 로그인 DAO 두 개로 구성했습니다. 자료에 첨부한 실행 결과에서는 오류와 실패가 모두 없음을 확인할 수 있습니다.

로그인은 성공과 실패를 구분했고, 상세 조회는 정상적으로 조회되는 경우와 해당 데이터가 없는 경우를 나누어 확인했습니다.

다만 목록의 검색 조건을 항목별로 충분히 검증하는 부분은 보완이 필요합니다. 다음 스프린트에서는 필터별 조건과 데이터가 없는 상황 등으로 테스트를 구체화하겠습니다.

## 22장 · 시연 [6:30~7:40]

지금부터 품질 담당자의 업무 흐름에 따라 로그인부터 목록, 상세 조회까지 보여드리겠습니다.

[6:30~6:45 · 준비한 계정으로 로그인]

먼저 품질 담당자 계정으로 로그인합니다.

[6:45~7:05 · 목록 화면에서 준비한 검색 조건 하나를 입력하고 조회]

로그인 후 보상 처리 지급결과 목록으로 이동합니다. 조건을 입력해 확인할 대상을 찾고, 조회된 항목 중 한 건을 선택하겠습니다.

[7:05~7:30 · 상세 화면에서 요약, 신청·산정·지급 정보를 차례로 표시]

상세 화면에서는 선택한 건의 요약과 피해신청 정보, 보상신청 및 산정 정보, 지급 결과를 확인할 수 있습니다. 담당자는 목록에서 찾은 건을 기준으로 관련 내용을 이어서 확인하게 됩니다.

[7:30~7:40 · 발표자료로 복귀]

여기까지가 이번 스프린트에서 구현한 핵심 사용자 흐름입니다. 이어서 진행 과정에서 배운 점을 말씀드리겠습니다.

## 23~24장 · 팀 회고 [7:40~8:45]

팀 회고는 소통, 분석설계, 구현 관점에서 정리했습니다.

유지할 점은 UI와 워크플로우를 근거로 의견을 조율하고, 협업 규칙과 업무 리스트를 문서로 남긴 것입니다. 구현에서는 페어 프로그래밍과 코드 리뷰를 통해 서로의 작업을 확인했습니다.

가장 어려웠던 점은 품질 담당자의 실제 업무를 이해하고, 팀원들이 같은 용어를 같은 의미로 사용하는 것이었습니다. 업무 해석이 다르면 UI 명세와 ERD도 달라졌고, 이를 다시 조율하는 데 시간이 들었습니다.

다음에는 회의의 목적과 판단 기준을 먼저 정하고, 합의한 용어와 설계 근거를 기록하겠습니다. 이해가 다를 때에는 그림과 업무 흐름으로 확인하겠습니다.

구현 측면에서는 목록 필터 테스트와 누락 기능을 보완하겠습니다. 한 페이지에서 여러 조회가 순차적으로 진행되는 부분은 비동기 처리의 적용 가능성도 검토하겠습니다.

## 25~28장 · 개인 회고 [8:45~9:35]

개인 회고에서도 업무 이해와 소통이 공통된 주제였습니다.

이재숙 님은 명확한 공통 용어와 UI, 워크플로우 같은 시각자료를 활용하는 소통의 필요성을 정리했습니다.

이원규 님은 업무 의도를 충분히 이해하고, 헷갈리는 부분을 바로 질문해 서로의 기준을 맞추는 것을 개선점으로 꼽았습니다.

김민경 님은 품질 담당자의 역할을 처음에는 검사와 검수 중심으로 해석했던 경험을 돌아봤습니다. 다음에는 상호 검토를 분석설계에도 적용해 세부 명세와 전체 업무 흐름을 함께 점검하려고 합니다.

박건태 님은 핵심 사용자와 메인 UI를 먼저 정의하고, 설계 의도와 기술 선택의 이유를 이해하며 소통하는 것이 중요하다고 정리했습니다.

[각 이름을 말할 때 해당 슬라이드로 전환합니다.]

## 마무리 · 28장 유지 [9:35~10:00]

이번 1차 스프린트에서는 품질 담당자의 로그인과 보상 지급결과 목록, 상세 조회를 구현했습니다. 또한 업무명세와 데이터 모델, 코드의 역할을 연결하고, 단위테스트로 조회 동작을 확인했습니다.

다음 스프린트에서는 이번에 확인한 누락 기능과 테스트를 보완하고, 공통 용어와 설계 검토 기준을 더 명확하게 적용하겠습니다.

이상으로 2조의 1차 스프린트 발표를 마치겠습니다. 감사합니다.
