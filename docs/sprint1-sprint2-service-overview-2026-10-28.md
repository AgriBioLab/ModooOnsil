# 1차·2차 스프린트 서비스 개요 — 생산자 정보와 피해보상 업무의 연결

작성일: 2026-10-28 / 최신 사용자 설명 기준

최신 범위 보정: '피해보상 신청 시 기존 기록을 활용하고 싶다'는 생산자 니즈에 맞춰 2차에 기존 기록을 활용한 피해보상 신청을 포함한다. 상세 기능과 UML은 [2차 UML 개념 설계 가이드](sprint2-uml-concept-guide-2026-10-28.md)를 기준으로 한다.

## 1. 전체 서비스 개요

**농업 관련 공공기관이 생산자 정보와 영농·재배 기록을 관리하고, 이를 생산자 지원과 피해보상 업무에 활용할 수 있도록 돕는 서비스다.**

생산자는 평상시 자신의 정보와 재배공정을 관리하고, 기관은 지원이나 피해보상 업무가 필요할 때 등록된 생산자와 영농현황을 찾아 활용한다. 1차의 품질담당자용 보상 모니터링과 2차의 생산자용 기능을 같은 기관이 제공하는 하나의 서비스로 연결한다.

기획의 중심은 기관 선정이나 AI가 아니라 **생산자 정보가 지원·보상 업무의 기반이 되는 관계**다. 노동력 감소·기후변화·디지털 전환은 생산자 서비스의 배경으로 설명할 수 있지만, 두 스프린트를 연결하는 핵심 목적을 대신하지 않는다.

## 2. 1차 스프린트 개요

> 농업 관련 공공기관의 품질담당자가 농산물 피해보상 처리 결과와 관련 정보를 조회하는 서비스입니다. 생산자별 피해·보상 내역을 확인하고, 향후 보상 통계와 품질 평가, 예측을 통한 전략 수립과 예산 책정에 활용하는 것을 목표로 합니다. 1차에서는 그 기반이 되는 로그인과 보상 지급결과 목록·검색·상세 조회를 구현했습니다.

| 항목 | 내용 |
|---|---|
| 액터 | 품질담당자 |
| 대상 업무 | 농산물 피해보상 결과와 관련 정보 모니터링 |
| 1차 구현 | 로그인, 지급결과 목록·검색·상세 조회, 로그아웃 |
| 전체 서비스의 후속 목표 | 보상 통계 분석·보상 품질 평가·예측·전략 수립·예산 책정 |
| 역할 경계 | 복구지원이나 보상금 지급을 직접 집행하는 역할로 설정하지 않음 |

구현 범위 근거: [1차 발표 스크립트](1차_스프린트_10분_발표스크립트.md), [1차 통합본 소스 리뷰](sprint1-latest-review.md). 통계·평가·예측·예산 기능이 모두 1차에서 구현됐다는 뜻은 아니다.

## 3. 2차 스프린트 개요

> 같은 공공기관의 서비스를 이용하는 화훼 생산자가 자신의 기본정보와 농장·품종·재배현황을 등록하고, 재배공정 및 출하이력을 관리하는 서비스입니다. 피해보상이 필요하면 기존 기록을 조회·선택하고 피해내용을 추가하여 신청할 수 있도록 합니다. 신청 접수 후 심사·금액 산정·지급은 별도 업무이며, 이후 지급결과를 1차의 담당자 조회 기능과 연결합니다.

| 항목 | 내용 |
|---|---|
| 이번 중심 액터 | 생산자(농민) |
| 서비스 제공자 | 1차와 동일한 농업 관련 공공기관 |
| 생산자의 업무 | 본인·농장·품목·재배현황과 공정 기록을 등록·조회·관리 |
| 생산자의 핵심 목표 | 기존 생산자·농장·재배·출하 기록을 활용해 피해보상 신청서 제출 및 접수 확인 |
| 생산자에게 주는 가치 | 본인의 영농현황을 파악하고 재배공정을 운영하는 데 기록 활용 |
| 기관 업무와의 연결 | 향후 지원·피해보상 시 생산자와 영농현황을 새로 파악하는 부담을 줄이고 기존 정보 활용 |
| 후속 범위 | 품질담당자 추가 기능, 보상 심사·금액 산정·지급 및 외부 연동은 이후 구체화 |

재배공정 현황·이력·환경 설정·조작 등 앞서 논의한 생산자 기능은 이 구조 안에서 상세 범위를 정한다. 최신 니즈에 따라 기존 기록을 활용한 피해보상 신청은 2차의 핵심·필수 기능으로 포함한다. 보상 신청과 금액 산정·지급을 구분한다.

## 4. 두 스프린트가 연결되는 이유

**생산자 정보 등록·갱신 → 평상시 재배·출하 기록 관리 → 기존 기록을 활용한 피해보상 신청·접수(2차) → 심사·산정·지급(후속 업무) → 지급결과 조회·모니터링(1차)**의 업무 흐름이다. 통계·평가·예측·예산 계획은 결과를 활용하는 후속 목표다. 이 흐름은 업무 순서이며 스프린트 개발 순서와 다르다.

1차에서는 보상 결과를 조회하는 담당자의 업무를 먼저 구현했다. 2차에서는 생산자의 정보·영농기록 관리와 기존 기록을 활용한 피해보상 신청을 설계한다. 신청 이후 심사·산정·지급 절차가 필요하므로, 신청만으로 지급완료 결과를 생성하지 않는다.

사용자가 든 산재의 예시는 **지원받을 사람의 정보가 준비돼 있으면 관련 업무에서 다시 활용할 수 있다**는 정보관리 관점의 비유로 반영한다. 특정 보험제도나 보상기관을 프로젝트의 제공기관으로 선정하는 근거로 확장하지 않는다.

### 정보 재활용의 예시

화훼 생산자가 본인과 농장·재배품종·재배구역을 등록하고 재배·출하 기록을 관리한다. 피해보상이 필요하면 본인·농장 정보를 불러오고 기존 이력을 조회·선택한 뒤 피해내용을 추가하여 신청한다. 심사·산정·지급을 거쳐 지급결과가 등록되면 품질담당자가 1차의 목록·검색·상세 기능으로 확인한다. 신청 시 참조한 기록과 이후 변경된 현재 기록은 구분하여 보존한다.

세부 데이터 항목은 명세에서 확정한다. 기존에 등록된 정보와 사건별로 추가 확인할 피해 내용은 구분하고, 현재 영농정보의 변경이 과거 보상 건의 기준정보를 덮어쓰지 않도록 설계한다.

## 5. 발표용 연결 문장

> 1차에서는 품질담당자가 피해보상 결과를 확인하는 기능을 구현했습니다. 2차에서는 화훼 생산자가 농장정보와 재배·출하 기록을 관리하고, 그 기록을 활용해 피해보상을 신청할 수 있도록 합니다. 두 스프린트는 동일한 생산자를 기준으로 신청의 기초정보와 보상 처리결과를 연결하는 서비스이며, 심사·금액 산정·지급은 별도 업무로 둡니다.

## 6. 이번 정리에서 유지하는 범위

- 동일 공공기관이 생산자용 서비스와 품질담당자용 서비스를 제공한다.
- 1차 구현 사실과 전체 서비스의 장기 목표를 구분한다.
- 2차의 중심은 화훼 생산자이며 정보·재배·출하 기록 관리와 기존 기록을 활용한 피해보상 신청을 포함한다.
- 품질담당자 추가 개발과 보상 심사·금액 산정·지급은 후속으로 둔다.
- 기관·AI·공공 발주 비교자료는 보조 근거로 보관한다. 현재 개요는 본 문서를 우선한다.
