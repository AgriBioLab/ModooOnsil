> 이전 20영업일 검토안이다. 사용자가 리팩토링 2일 + 스프린트 15영업일로 지정했으므로 최신 일정은 [15영업일 타임라인](sprint2-timeline-15days.md)을 기준으로 한다.

기준일: 2026-10-21 (Asia/Seoul)

상태: 권장 일정. 팀·강사 확정 일정이나 실제 구현 완료 기록이 아니다. Google Slides와 Jira는 수정하지 않았다.

## 일정 권장안

- 사전 리팩토링: 2026-10-22(목)~10-23(금), 2영업일.
- 2차 스프린트: 2026-10-26(월)~11-20(금), 20영업일 권장.
- 합계: 사전 준비 2일 + 스프린트 20일 = 22영업일.
- 영업일 계산은 월~금 기준이다. 교육 휴무·개인 부재·확정 발표일은 별도 반영한다.
- 이 기간은 현재 합의한 기능과 Spring 전환을 함께 다루는 검토 기준이다. 팀원 수·실제 가용 시간·Spring 숙련도·API 사양·파일 저장 상태가 미정이므로 인력 투입량으로 검증한 확정 추정은 아니다.
- 10/23 전환 기반 점검, 10/30 기능별 명세·환경 점검, 11/6 중간 시연, 11/13 신규 기능 구현 동결 목표, 11/18 통합 검증 점검, 11/20 제출 준비 완료 목표를 둔다.

‘전체 전환 완료’를 사전에 가정하지 않고, 금요일 결과로 실제 잔여 작업을 판정한다.

| 날짜 | 작업 | 확인할 결과 |
|---|---|---|
| 10/22(목) | 기존 동작 기준 고정, Spring·JDK·Tomcat·빌드·DB 접근 방식 선택, API와 파일·비밀번호 재설정의 기술 의존성 확인 | 팀원이 재현할 실행 설정, 대표 기능 선정, 미정 기술 항목·막힘 기록 |
| 10/23(금) | 대표 조회 기능을 요청·Controller·Service·DAO·DB·화면까지 연결, 자원·예외·세션 처리 책임 정리 | 정상 조회·빈 결과·DB 오류 구분 확인, 로그인 상태와 기존 조회 결과 비교, 변경 구조와 실행 가이드 리뷰 |

기존 목록/상세 중 대표 기능을 선택한다. 금요일에 전체 기존 기능 전환까지 검증했다면 스프린트 첫 주의 전환 작업을 줄인다. 기반만 검증했다면 나머지 기존 기능 전환을 스프린트 업무로 명시한다. 서버가 켜지는 것만으로 전환 완료로 처리하지 않는다.

## 기능 범위와 기술 우선순위

P0는 다른 작업의 선행 조건, P1은 현재 합의한 기능의 완료 범위다. P1이라고 제출 이후로 미룬다는 뜻은 아니다.

| 우선순위 | 범위 | 선행 확인·완료 기준 |
|---|---|---|
| P0 | Spring 실행·공통 요청·DB 접근·자원·예외 처리 | 대표 흐름 실행과 오류 구분, 기존 기능 회귀 기준 |
| P0 | 계정·역할·본인 데이터 접근 | 품질담당자/생산자 식별과 권한 기준, 타인 신청 조회 차단 |
| P0 | 공공 API·집계·서류·재설정 방식 기술 분석 | 실제 API 코드/명칭·이용 조건, 집계 날짜/상태·비교 기간, 파일 위치/형식, 본인 확인 방식 결정 |
| P1 | 생산자 가입·로그인·피해신청·본인 신청 조회 | 사용자 식별, API 코드 매핑, 신청 저장, 본인 목록/상세 범위 확인 |
| P1 | 품질담당자 통계·전년도 대비 비교 | 원천 데이터와 집계값 대조, 전년 동기 여부, 전년도 0/빈 결과 처리 |
| P1 | 기존 보상 지급결과 상세의 서류파일 열람 | 실제 파일과 해당 지급 건 연결, 권한, 파일 없음·잘못된 경로 처리 |
| P1 | 마이페이지·비밀번호 찾기·변경 | 표시 정보·본인 확인·재설정·변경 후 로그인 시나리오 확인 |
| 공통 | 명명·패키지·문서·테스트·PR 기준 | UI·ERD·SQL·코드의 용어 대응, 검증 결과와 변경 근거 기록 |

사용자 범위에 없는 신청 수정·취소, 담당자의 승인·지급 업무, 자동 예산 산정·예측은 기본 일정에 추가하지 않는다. 성능 개선은 실제 병목과 필요성을 확인한 후 별도 추정한다.

## 11/6 중간 점검에서 기간을 판단하는 기준

- 대표 Spring 기능뿐 아니라 기존 로그인·검색·상세·로그아웃 흐름을 확인했는가.
- API 실응답의 코드를 선택해 피해신청을 DB에 저장할 수 있는가.
- 생산자의 본인 조회와 권한 검증을 시연할 수 있거나 구현 완료일이 근거 있게 추정되었는가.
- 통계·전년도 비교의 원천 데이터와 집계 기준이 맞고 핵심 조회가 실행되는가.
- 서류 실제 파일, 비밀번호 본인 확인·재설정 방식에 미해결 외부 의존성이 남아 있는가.
- 남은 필수 업무가 각 담당자의 가용 작업일에 들어가는가. 통합·검증·보고 시간을 남겼는가.

미해결 선행 조건이 있으면 11/20을 조용히 유지하지 말고 강사와 범위 또는 종료일 조정을 논의한다. 15영업일(11/13) 종료는 현재 전체 범위의 기본안으로 잡지 않는다. 조기 완료는 검증 결과로 판단한다.

## Jira 운영안

대상: [공유한 SCRUM 프로젝트](https://tlals0028.atlassian.net/jira/software/projects/SCRUM/summary)

현재 Atlassian 연결 두 개 모두 재인증을 요구해 기존 이슈·보드·스프린트를 조회하지 못했다. 아래는 실제 생성한 업무나 스프린트가 아닌 설계안이며 기존 이슈 중복 여부 확인이 필요하다.

1. 사전 작업 10/22~23은 별도 준비 구간으로 표시한다.
2. 강의에서 부르는 ‘2차 스프린트’는 10/26~11/20의 보고·제출 단위로 둔다. 실제 Jira 스프린트를 하나로 둘지, 중간 점검을 경계로 10/26~11/6과 11/9~11/20 두 개로 운영할지는 팀 규칙에 맞춘다. 팀이 처음 도입한다면 명칭 혼선을 줄이기 위해 하나의 기간과 주간 점검부터 시작할 수 있다.
3. Epic은 Spring 전환·생산자 신청·품질 통계/비교·서류/계정·통합검증처럼 결과물 기준으로 나눈다. 분석·설계·구현·검증은 각 Epic 아래의 작업으로 둔다.
4. Task는 실행·검증 가능한 결과물 단위로 나누고 담당자, 시작일, 완료 목표일, 추정 작업량, 완료 조건, 선행 작업, 원본 문서·PR 링크를 기록한다.
5. Timeline에서 Epic과 하위 업무의 날짜·의존관계를 보고, 보드에서 할 일 / 진행 중 / 리뷰 / 검증 / 완료를 관리한다. 실제 표시 범위는 프로젝트 유형과 설정을 확인한다.
6. GitHub 연동 후 기존 브랜치 규칙에 Jira 키를 덧붙이는 방식(예: `feat_SCRUM-123_disasterCode`)을 팀 합의한다. 커밋·PR에도 키를 넣어 개발 정보를 연결한다. 이 예시는 실제 생성한 이슈 키가 아니다.
7. PR 병합만으로 완료를 판정하지 않고 업무별 검증과 문서 반영까지 확인한다. 자동 상태 전환은 연결만으로 확정하지 않고 별도 설정과 검증을 거친다.

일정 상태의 기준은 Jira 한 곳에 두고, 스프레드시트와 Notion에 같은 상태표를 중복 운영하지 않는다. 별도 문서 도구는 회의록·결정 근거를 기록하고 Jira 업무 링크를 붙인다.
